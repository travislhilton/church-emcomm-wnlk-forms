# Church of Jesus Christ EMCOMM Simulator — design

This emergency communications (EMCOMM) simulator is part of an independent volunteer project, not an official product or publication of The Church of Jesus Christ of Latter-day Saints. It exercises the forms, the EOC (Emergency Operations Center) Message Center and the PACE communications plan ([PACE_PLAN.md](PACE_PLAN.md): Primary cellular, Alternate any internet anywhere, Contingency radio by Winlink over VARA FM then VARA HF, the sound-card radio modem Winlink uses, plus voice, Emergency runner) with realistic traffic, so that volunteers, HAM (amateur radio) operators and EOC workers can practise before a real event.

Companion documents: [SCENARIO_AUTHORING.md](SCENARIO_AUTHORING.md) (how to write a scenario, step by step, with the field reference), [SIMULATOR_SCENARIOS.md](SIMULATOR_SCENARIOS.md) (the scenario catalog of the invented example community, the Juniper Plains Area; a real community keeps its own catalog beside its directory export) and [SIMULATOR_MAPS.md](SIMULATOR_MAPS.md) (how the geographic dataset is placed on a map). Code lives in `simulation/`.

## 1. What the simulator is for

Three exercise sizes, from the maintainer's brief (2026-10-30):

| Size | Who | Systems | What is exercised |
|---|---|---|---|
| **Tabletop** (a few workers in one room) | 2 to 6 people playing every role in turn | One laptop as the Stake EOC, one playing the lines above it (council and welfare line, or a Council / Area EOC), workers' own laptops and phones as field devices | Choosing an event, the simulator feeding reports, PACE changes and everything that reacts to them, submitting reports through every path (phone app, Drop Folder email, Winlink, typed from voice, paper), viewing and managing lists, escalating up the chain |
| **Stake drill** (wards and branches take part) | Stake President, specialists, bishops, Team Leaders, HAMs, EOC workers | Stake EOC on a laptop at the stake center with Starlink; a Satellite EOC in a ward building; a laptop also at the stake center playing the council and the welfare line (or a Council / Area EOC) | The same, with real volunteers in the field, real radios on the stake net, the Satellite EOC rolling up to the Stake EOC, PACE stepped down and back up with the round-trip test |
| **Council / Area drill** | Several stakes, both coordinating councils, the Area roles | One simulator and EOC per participating stake and satellite; one or two laptops playing the welfare line and the councils (Council / Area EOCs if the drill opens them) | Many stakes reporting at once; the Area roll-up; Supply Order approvals coming back down; stakes in more than one county or state |

Design rules that follow:

1. **The simulator never replaces the real system.** Every simulated report enters the EOC by a path a real report could take (phone upload, Drop Folder file, Winlink `.mime` file in the Received folder, or a paper card someone types in). The EOC software does not know it is being drilled, except that the event is named as a drill.
2. **One simulator per EOC laptop.** Each EOC runs its own simulator web app on the same laptop, with the same scenario selected and the same start time. The Satellite simulator generates traffic only for the units that EOC covers; the Stake simulator generates the rest; the Area simulator generates the stakes that are not being played by people.
3. **PACE is driven by the scenario** on a timeline, announced to the role players, and applied to the EOC (`PUT /api/incident`, field `pace`) so the header, the Help page and the SITREP (situation report) react. Role players still perform the human steps: the specialist recommends, the Stake President decides, the net announces.
4. **The organization is data, not code, but the drill uses its real names.** Units, stakes, councils, buildings and contacts come from an *organization pack* loaded at run time from a folder outside the repository (`secure data/` here). On screen, in every message and on every card the simulation uses the real ward, branch and stake names as CDOL (the Church Directory of Organizations and Leaders) lists them: that is what makes a drill feel real (maintainer, 2026-10-30). A scenario names **geography** (a river bottom, a canyon road, a bridge, a dam, a highway) and fills unit, stake, bishop and building names from the pack through placeholders. The repository holds only the invented example community and its scenarios (`simulation/example/`, `simulation/scenarios/`); a real community's scenarios name its real places and therefore live beside its directory export (`<export>/simulation/scenarios/`, read by the simulator before the built-in ones), never in the repository. Unit-specific story lines written by hand for this dataset (which ward loses its parapet, which ward asks for the Satellite EOC) go in a **local binding** file beside the data (`<pack folder>/simulation/<scenario>.local.json`, git-ignored), which the engine merges when present. Another area later gets its own pack and its own binding; the repository never carries organization names.
5. **Two privacy modes** (section 5): real contacts for realism, or pseudonymized contacts for anything that leaves the room.
6. **No new runtime dependencies** (repository rule 7): the simulator is one Python standard-library server and one self-contained web page (HTML), like the EOC.

## 2. Pieces

```
simulation/
  sim_server.py        web app server: page, dataset files, organization pack, scenario runs (port 8090)
  start_simulator.bat  launcher (installer role 3 puts simulation\ under EOC Message Center\, next to eoc_server.py)
  index.html           the simulator page: map, scenario picker, run control, role cards, drill feed
  orgpack.py           loads a CDOL export (or a prepared pack JSON) into one normalized OrgPack

  scenarios/
    catalog.json       every scenario: id, hazard, summary, where it applies
```

CDOL is the Church Directory of Organizations and Leaders; its export format is the one documented in the dataset's own `README.txt`.

### 2.1 Organization pack (`orgpack.py`)

Built from a CDOL export folder (`csv/*.csv` + `simulator/*.geojson`) or read directly from a prepared `orgpack.json` with the same shape, so an area without a CDOL extract can write the JSON (JavaScript Object Notation) file by hand or from a spreadsheet.

```
pack = {
  "kind": "church_emcomm_orgpack", "v": 1, "source": "<export name>", "privacy": "real" | "pseudonymized",
  "councils":  [{id, name, stakes:[id], leaders:[contact]}],
  "stakes":    [{id, name, council, center_building, units:[id], state, county?, leaders:[contact], email?, phone?}],
  "units":     [{id, name, type: "Ward"|"Branch", stake, building, lat, lon, city, state,
                 flags: ["language_unit","care_facility","retirement"], draws_from:[stake ids], boundary_bbox, leaders:[contact], phone?}],
  "buildings": [{id, address, city, state, lat, lon, units:[id], stake_center_for:[stake ids], phone?}],
  "welfare":   {region:{name, manager:contact, office_building?}, area_office:{name, awsrm:contact}},
  "contacts":  [{id, person, role, org, first, last, mobile?, phone?, email?}]
}
```

Every contact keeps its CDOL person id so a pseudonym is stable across runs. Nothing from a pack is ever written under the repository; packs and generated runs live beside the source data (default `secure data/runs/`) or in a folder the user picks.

**Roles the directory does not list** (2026-10-30): the CDOL export has no emergency callings. `orgpack.load()` also reads `<pack folder>/simulation/local-roles.json` (`church_emcomm_local_roles`: `roles[] = {org, role, first, last, mobile, phone, email, note}`), appends each as a contact (`id local-<n>`, `local: true`) and leader of its organization (council, stake, unit, welfare region or area office), so `Index.erd()` / `Index.specialist()` and the template values `{erd}`, `{erd_phone}`, `{specialist}`, `{specialist_phone}` resolve. The Setup tab edits the file (`GET/PUT /api/local-roles`, which reloads the pack); pseudonymization treats them like every other contact. `REQUIRED_ROLES` / `required_status(pack, site)` list the roles an EOC cannot run without (by level; source directory / local / room) with who fills each; the Setup tab shows them under "What this simulator plays" with Add buttons, and the live Message Center's Setup tab has the same list as `MUST_ROLES` (names and phones stored in `incident.roles`, highlighted until filled).

### 2.2 Scenario (`scenarios/<id>.json`)

A scenario is geography plus a timeline, with no organization names in it. Section 4 gives the schema; `copper-creek-dam.json` (the invented Juniper Plains Area) is the fully developed public example. The catalog entry says which areas it applies to (a bounding box the pack must overlap) so a pack from one valley is not offered another valley's dam failure.

### 2.3 Engine (`engine.py`)

`plan(pack, scenario, options) -> run`:

1. **Scope**: which units this simulator plays. Defaults to the units of the EOC it is attached to (read from the EOC's `/api/incident` `eocUnits`, or chosen on the page); the Area simulator's scope is "stakes not played by a person".
2. **Severity per unit**: the scenario's severity rule (distance from an epicenter, inside a flood or fire polygon, a flag such as `care_facility`) gives each unit a band 0 to 3.
3. **Injects**: each scenario inject expands per unit (or per stake, or once) into concrete messages at a concrete minute, with the template's per-severity value ranges resolved and placeholders filled (`{unit}`, `{city}`, `{building}`, `{bishop}`, `{stake}`, `{river}`). The result is the exact Worker-form field set the EOC already accepts, so the EOC maps it like a phone upload.
4. **Channel by PACE**: the delivery path is chosen from the PACE level in force at that minute unless the inject fixes one:

   | Level in force | How the simulated report arrives | What the EOC sees |
   |---|---|---|
   | P | `POST /api/upload` (phone app) or a `.txt` in the Drop Folder (emailed file) | Via *Phone / browser* or *Internet drop* |
   | A | same as P | same |
   | C | a Winlink `.mime` message written into the watched Received folder (the EOC's Winlink auto-ingest picks it up), addressed from the unit's HAM; voice traffic becomes a **net card** the HAM role player reads over the net and the operator types in | Via *Winlink* (radio) or typed |
   | E | a **paper card** on the simulator screen: "a runner arrives with this form"; the operator types it into the Message Center | manual entry |

   The `.mime` path uses the same `[Church-XX|…]` tagged body the Winlink templates produce, so the EOC parses it with the code it uses for real radio traffic.

   The runner pushes each step of the scenario's PACE timeline to the EOC (`PUT /api/incident`, field `pace`) the moment it comes into force, once per step, and logs it ("PACE C in force (scenario timeline): EOC header set"); a level the controller sets by hand is pushed at once and replaces the later scheduled steps (2026-10-30).
5. **Run file**: `run.json` = scope, privacy mode, every inject with its minute, channel, payload and status. Saved beside the pack so a run can be replayed or inspected after the drill.

`Runner(run, eoc_url, …)` runs the clock (real time or a speed factor), fires injects when due, records the EOC's answer (new / duplicate / error), applies PACE changes to the EOC, and posts scenario notes to the EOC's log (`POST /api/notes`) so the Messages and wall views show "06:44 Aftershock M5.1 reported" the way an operator would log it.

### 2.4 Simulator page (`index.html`)

Tabs, left to right, in the order a controller uses them:

0. **Session** (built 2026-11-01; the page opens on it) — the trainer's path in five steps: (1) before the meeting, set up and rehearse; (2) **Reset for the session**: the rehearsal stays a rehearsal, a fresh drill event opens on the EOC, the run is planned again at T+0, PACE is set to the scenario's first level and every EOC screen shows *ready: waiting for the trainer's GO*; (3) **GO** (or one scheduled start on every laptop), which starts the EOC's SITREP clock; (4) live: clock, phase, PACE, score, what comes next; (5) finish: the hot wash, the after-action report, the **debrief** (`/debrief`) and the **results** (`/results`). The run saves itself every 30 seconds; **Resume** brings an interrupted session back paused (`/api/session`, `/api/session/reset`, `/api/session/go`, `/api/session/resume`, `/api/sessions`).
1. **Setup** — organization pack (path, loaded counts, privacy mode with a visible badge on every page when real contacts are loaded), EOC this simulator feeds (URL, its web address, from discovery, level, units covered), scenario picker (catalog with hazard, duration, "applies here"), speed, start time.
2. **Map** — the map built this session: boundaries, buildings, overlay images, geodesic measuring; during a run it shows severity per unit, injects as they fire, and the EOC's roster status fetched from the EOC (`/api/roster`).
3. **Run** — the controller's console: clock, PACE in force with the next change, the **scoreboard** (needs met / overdue / score / minutes to an owner / HIGH without an owner, the done-when checks), phase narrative, the inject list (fired / due / pending / waiting on a need, with Fire now / Skip / Hold / Force now), net cards and paper cards to hand to role players, the EOC's answer per inject.
3a. **Needs** — the ledger of what the EOC owes (section 2.7): state, deadline countdown, evidence, accuracy of typed-in reports, Waive / Reopen.
4. **Roles** — one card per role (Stake President, Welfare and Self-Reliance Specialist for emergency communications, Emergency Response Director, Bishop, Team Leader, HAM at a ward, EOC operator, Satellite EOC operator, Council / Area EOC operator, the welfare line: the Welfare and Self-Reliance Manager (WSRM) and the Area Welfare and Self-Reliance Manager (AWSRM); the Area Seventy): what they do at each phase, what they should notice, and the scripted lines a role player reads when the scenario calls for a voice report or a decision.
5. **Hot wash** — the evaluation checklist from the scenario (did SITREP #1 go within the interval, did the step-down follow a trigger, did the missionaries alert get acted on), filled in by the controller during the run, exported as text for the feedback issue template; the **After-action report** and **Debrief** buttons (section 2.7).

### 2.5 Multi-EOC coordination

Built 2026-10-30. **One simulator per EOC in the drill**; each drill director says what theirs plays.

- **What this simulator plays** (Setup tab, section 2): a **Stake EOC** (the stake, and the wards a Satellite EOC covers in this drill), a **Satellite EOC** (the stake and the wards it covers; the scenario can suggest them through `eocs.satellite.where`, served by `GET /api/scenarios/<id>?stake=<id>`), or a **Council / Area EOC** (one or more coordinating councils, and which of their stakes have their own EOC laptop in the drill). The scope follows the role; the choice is remembered in the simulator's settings and shown as the run's `site` (role, label, parent, units).
- **Routing.** Every planned item carries `to` (`stake`, `satellite`, `area` or `all`) and `local`. Reports follow their unit to the EOC that covers it; notes and cards go to every EOC (each simulator posts them to its own); work items go to the Stake EOC unless the inject says `to`; items another EOC's simulator plays are shown as **elsewhere** and never fired here. Choosing the same scenario and seed on every simulator makes every site plan the same minutes and the same sampled units.
- **Roll-ups at the Council / Area EOC.** `rollup` injects (in the first developed scenario: twice, after each SITREP time) expand to one item per stake the Area simulator plays itself (no EOC laptop). When one fires it bundles that stake's reports due so far into a `church_eoc_rollup` (records with summary fields only, `origin` / `via` "<Stake> EOC (simulated)", the roster, a SIM note, the Supply Order and headquarters-assistance work items as UP) and writes it as a file into the Area EOC's **Drop Folder** (the path the EOC reports when it is checked), so the watcher ingests it within ten seconds and moves it to `Ingested\`, exactly the way an emailed roll-up arrives; when that folder is not reachable from the controller laptop it falls back to `POST /api/merge` and the Run tab says so. Stakes with their own laptop send their real roll-ups themselves (email, Winlink attachment or USB, Universal Serial Bus, drive), and if they do not, the Area never sees them: that is what the drill tests. Reports dated after a simulated stake's last roll-up have no roll-up left to ride in: when everything else is done the run marks them *skipped* ("no roll-up from its stake after it before the end of the drill") and ends, instead of waiting for ever (2026-11-13.3).
- **Drill state on every screen.** The simulator PUTs its state to its EOC's `/api/drill` every five seconds (role, label, parent, scenario, seed, status, elapsed minute, speed, start time, controller URL); `/api/status` carries it as `drill`; the Message Center, wall display and phone page show a **drill bar** (scenario, what this EOC plays, T+ or the countdown, who is ready) and a role mismatch against the Setup tab's level. Operators press **I am ready** (`POST /api/drill/ready {who}`); the names ride back to the simulator. `DELETE /api/drill` clears it (the simulator does so on exit).
- **Coordinating the start.** The Run tab's **EOCs in this drill** board lists this EOC and every EOC its server hears on the network (`/api/peers`), each with what its simulator plays, scenario, seed, clock state and Ready names, and flags a different scenario, seed or start time, a Setup level that differs from the simulator's role, and an event name without DRILL. **Schedule** (`POST /api/run/schedule {at: "HH:MM:SS"}`) starts the clock at a wall-clock time; every simulator set to the same time starts together, which needs no network between sites. Remote sites report ready by voice on the net.
- The region / council reality from the organization analysis (finding F1: two upward addressees, the Area Seventy's council and the welfare line, and no standing Area EOC) is in the software since 2026-10-30: the Message Center's Setup tab holds both lines and the SITREP header lists them; the top level is "Council / Area EOC", used only when the council or the welfare region opens one. The scenario has a council role card, a welfare-line role card and a Council / Area EOC card used only when the drill opens that EOC.

### 2.7 Evaluation: the needs ledger, consequences, replies, scoreboard, after-action report

Built 2026-10-31. Until then the simulator could tell the controller *what it sent* but not *whether the EOC coped*: the hot wash read five checks, nothing in the world reacted to what the EOC did, and nothing came back down from the line above. The evaluation model adds a **world that answers**.

- **A need per thing the EOC must do.** When an item fires, the engine registers what the EOC owes for it: every scripted `work_item` (one need, matched by its key `sim:<item>`), every work item the EOC *derives* from a simulated report (the engine runs the server's own `_derive_actions` on the payload: injuries, missionaries, headquarters assistance, neighbouring unit, local facilities, shelter, building damage, Supply Order approval), every paper or net report a person must **type in** (`kind: report`, matched by unit + form), and any card with a `need` block (the gas smell: a work item with "gas" in the title; the satellite question: a facilities item with the decision written in). Each need has a category, a priority, a label, a role, and a **rule** in drill minutes: `owner` (owned within), `done` (closed within, counting `up` as done where the line above must answer), `decision` (the decision text must be filled in at DONE), `typed` (a report typed in within). Rules come from the scenario's `needs.defaults` per category (`NEED_DEFAULTS` in the engine when a scenario has none), overridden per inject.
- **The ledger ticks.** Every 4 s (and after any fire) the runner reads the EOC's `/api/actions`, `/api/messages` and `/api/incident` and moves each need through `open → met | late | overdue | missed` (`waived` by the controller takes it out of the score). Evidence is written in words ("appeared T+5; owner Pat after 15 min (limit 10); done after 40 min"); times map wall clock → drill minute through the clock segments (§2.3), never before the need arose. A typed-in report is compared field by field with the card the runner carried (`compare_truth`: numbers, yes / no, text, case-blind), and the evidence names the wrong fields ("injured: typed 13, card said 12").
- **Consequences and resolutions** (`after` on an inject): `{"need": "<inject>[#kind]", "is": "met" | "overdue", "delay": minutes}`. The item plans as `waiting` and is scheduled only when the need reaches that state; `each: unit` binds it to the unit's own need when the need is per unit, and a per-unit item may wait on a stake-wide need (the west-side relayed reports wait on the one relay-plan item). A `form` may be a consequence too (the walk-up crew's log, the relayed reports). For example: the shelter decision → the Emergency Response Director's (ERD's) note (8 min); the county headcount → the Red Cross trailer; the delivery point → the storehouse truck leaves; an injuries item closed → county dispatch confirms care. Overdue: the Stake President calls again with a tighter re-ask item, the mission president comes on the county liaison's line, the county asks again, the WSRM holds the storehouse truck, the bishop asks over the net who has the injured list, the clerk is back at the door about the paper report. Nothing is forced: the players earn either path.
- **Replies from the line above** (`kind: reply`): the simulator plays the welfare line (WSRM, AWSRM) and the Council / Area EOC unless the Setup tab says **people play the line above** (`site.played_parent`; a Satellite EOC's parent is always played). A reply is a `church_eoc_reply` bundle (`replies: [{id, key, title, status, decision, text}]`, `notes`, `from`) POSTed to the EOC's `/api/merge`; the server closes each matching item (by id, then key, then the title of a waiting item) with the decision written in, a log line "Reply from <sender>" and `replied`. For example: each Supply Order set UP is approved 25–30 drill minutes later (`r-so-care`, `r-so-water`), a headquarters-assistance request is acknowledged (`r-hq`), and the T+185 sweep (`n-approvals`) answers whatever is still UP. The same path serves real drills: on a Council / Area EOC or Stake EOC the Message Center offers **Reply to <EOC>** on every item that came up in a roll-up; the reply downloads as a JSON file and travels back the way the roll-up came (Winlink attachment, USB, Drop Folder, LAN, the local network); the lower EOC merges it like a roll-up.
- **Scoreboard** (`Runner.score()`): counts by state and category, `pct = (met + ½ late) / scored` (scored = met, late, overdue and missed: a need still open inside its time is in `total` but not scored yet, so the room does not read "0 %" right after GO; MISSED is set once, when the run ends, and later refreshes of `/results` or the report leave it), a label (strong ≥ 85, steady ≥ 65, struggling ≥ 40, overwhelmed), the trend against ten drill minutes ago, median minutes to an owner and to done, reports expected / sent / typed in with accuracy, SITREP times (from the EOC's `lastSitrepTs` through the clock), HIGH needs without an owner, and the scenario's **done-when checks** (`done.checks`: `sitrep n by T`, `no_unowned_high`, `pct_min`, `cat_met`; a dated check is *pending* until its deadline). It is in the run state (`/api/run`), in the drill state pushed to the EOC (so the Message Center, wall and phone DRILL bars read "Needs met 7/14 · 2 overdue · 46%"), on the Run tab (tiles, bar, chips) and in the header. The **Needs tab** is the controller's ledger: state badge, deadline countdown, evidence, accuracy, Waive / Reopen, filters by state and category.
- **After-action report** (`Runner.report()`, `report_text`, `report_html`): run header, scoreboard, by-category table with the role responsible, done-when checks, the **do-better list by role** (every need not met on time, with the evidence and a coaching line from `NEED_COACH` keyed by category and failure: owner, done, decision, typed, accuracy), what went well, the needs ledger, the hot-wash answers with evidence, the timeline from the log. Served at `/report` (printable HTML), `/api/run/report` (JSON, `?format=txt|html`), `/api/run/report.txt`; written as `run-<id>-report.html` and `.txt` beside the run file when the run finishes or is stopped. The Hot wash tab has the buttons.

- **Debrief for the room** (`engine.debrief_html`, served at `/debrief`; built 2026-11-02): a self-contained slide show for the projector, built from the after-action report. What went well first; the honest score; why it matters (the `lesson` lines of the injects behind what was missed, from [SIMULATOR_LESSONS.md](SIMULATOR_LESSONS.md)); one or two things per role; the group's progress over its runs of the same scenario; the next drill. ← → (or space, or a click) to move, F full screen, P print one slide per page. Linked from the Session tab (step 5) and the Hot wash tab. `/results` is the read-only scoreboard for phones in the room.

Scoring stays mechanical and transparent: every number on the scoreboard has a need with evidence behind it, and the controller can waive anything the room did not play.

### 2.6 Deployment

- `simulation/` ships in the repository and in the Forms ZIP and one-file installer under role 3 (EOC Operator), installed as `EOC Message Center\simulation\` with `start_simulator.bat` and a Desktop shortcut *Church of Jesus Christ EMCOMM Simulator*. It needs the same Python the EOC server needs.
- The organization pack is never shipped. On first start the simulator asks for the pack folder (or `orgpack.json`) and remembers it in a local settings file next to the server, outside the repository.
- Generated runs, pseudonym tables and hot-wash exports go to a folder the user picks (default next to the pack). The one-file installer, the ZIP and GitHub Pages carry only code, scenarios and documentation.

## 3. A run, minute by minute (tabletop size, Stake EOC)

1. Controller starts the EOC server and the simulator on the Stake laptop, opens a drill event on the EOC ("Drill — Copper Creek Dam failure"), loads the pack in pseudonymized mode, picks the scenario, scope = the stake's units, speed 2x.
2. Role players open the EOC Message Center (operator), the phone page on their phones (Team Leaders), Winlink Express with the Church templates (HAM), and the simulator's Roles tab on a shared screen.
3. T+0: the simulator posts the opening note, sets the EOC event's PACE to P, shows phase 1. The first reports arrive by phone upload (P). Players practise the normal path.
4. T+6: scenario says the cellular network is failing; the specialist role card says "recommend C; two failed attempts in 15 min"; the Stake President role card says "decide and have the net announce it"; the controller confirms the step-down on the Run tab (or lets the timeline do it). The EOC header turns to C.
5. T+6 to T+60: reports arrive as Winlink files; net cards go to the HAM player who reads them on the (simulated) net; the operator types them in; a paper card arrives by "runner" from the unit with no HAM. The roster fills; the missionaries alert fires for one unit; a Supply Order arrives; the operator generates SITREP #1 and sends it up (the Area laptop receives it).
6. T+90: Starlink is up at the stake center (A for the EOC's own internet); SITREP #2 goes by email; Winlink Telnet; the step-up round-trip test is a scripted inject.
7. T+150: cellular returns in part; step up to P after the test; late reports and Work Crew Logs; T+180 hot wash from the checklist.

## 4. Scenario file schema

```json
{
  "id": "copper-creek-dam", "name": "…", "hazard": "flood", "v": 1,
  "summary": "…", "sources": ["…"],
  "applies": {"bbox": [west, south, east, north]},
  "clock": {"t0": "Tuesday 06:42 local", "duration_min": 240, "default_speed": 2},
  "geo": {"epicenter": [lat, lon], "features": {"<name>": {"type": "polygon", "coords": [[lon, lat], …]}}},
  "severity": {"rule": "distance_km", "from": "epicenter", "bands": [{"max": 8, "level": 3}, …], "boost": [{"in": "<feature>", "add": 1}, {"flag": "care_facility", "min": 2}]},
  "pace": [{"t": 0, "level": "P", "why": "…"}, {"t": 6, "level": "C", "why": "…", "trigger": "…"}, …],
  "phases": [{"id": "impact", "from": 0, "to": 30, "title": "…", "narrative": "…", "controller": "…"}],
  "injects": [
    {"id": "dr-initial", "kind": "form", "form": "dr", "each": "unit", "t": {"from": 8, "to": 45},
     "template": "dr_initial", "channel": "by_pace", "note": "…"},
    {"id": "aftershock-1", "kind": "note", "t": 23, "text": "…"},
```

- `each`: `once` | `unit` | `stake`. `where` filters by severity, flags, feature membership or a random sample; `tag` names the sampled units for `same_as`, and `tag_not` excludes the units an earlier inject sampled under that tag (for example, a cut-off unit sends no follow-up report or crew log). `t` is a minute or a `{from, to}` window spread uniformly. `lesson` (optional, any inject) is the one-line real-world evidence behind it ([SIMULATOR_LESSONS.md](SIMULATOR_LESSONS.md)), shown with the card.
- **Local binding** (`<scenario>.local.json`, outside the repository): the same shape, merged over the scenario (`engine.merge_local`): `geo.features` and `templates` are added or replaced by name; `injects` replace the scenario's inject of the same `id` or are appended (they may name units with `where.unit` / `where.units`); `roles`, `hotwash` and `phases` replace the scenario's lists when given; `severity_override` (`{"<unit name>": band}`) and `agencies` are merged; `notes` is kept as `local_notes`. Everything the engine produces still comes out with the pack's names either way.
- Template values (`engine.resolve`): a literal string (placeholders filled) or number; `{"range": {"<band>": [min, max]}}` an integer drawn per report; `{"pick": {"<band>": ["…", …]}}` one text picked at random; `{"yes": {"<band>": p}}` YES with probability p, else NO. A band missing from the map falls back to the nearest lower band given, then the lowest. Bare band maps without `range` / `pick` / `yes` resolve to an empty value. Supply Order `items` take `{"range": {"<band>": {"<catalog id>": [min, max]}}}`; Work Crew Log `crew` takes `{"count": {"<band>": [min, max]}, "hrs": {…}, "wo": {"pick": {…}}}`. Placeholders are filled from the unit and pack.
- `channel`: `by_pace` (section 2.3), or fixed: `phone`, `drop`, `winlink`, `paper`, `voice`.
- `eocs` (optional): `{"satellite": {"name": "…", "where": {…}}, "area": {"name": "…"}}` — the wards a Satellite EOC would cover (a `where` clause, offered as a suggestion on the Setup tab) and what the drill's Council / Area EOC is.
- `to` on any inject: `stake` | `satellite` | `area` | `all` — which EOC of the drill it is for (default: reports follow their unit, notes and cards go everywhere, work items to the Stake EOC, roll-ups to the Council / Area EOC). The older `"to": "eoc"` on notes is read as `all`.
- Inject kinds: `form` (a report), `note` (EOC notes log, prefixed `SIM:`), `voice` (net card for a HAM), `prompt` (a card for a role player), `paper` (a card for a runner), `rollup` (Council / Area simulator only: a `church_eoc_rollup` bundle per stake it plays itself, with the reports due so far), `work_item` (posted to the EOC's `/api/actions`: a request or decision the reports cannot derive, with `title`, `detail`, `next`, `cat`, `prio`, `due`, `from`; the key `sim:<item id>` keeps it from doubling; `same_as` / `each: unit` fill `{unit}`, `{bishop}` and the rest).
- Hot-wash `auto` rules are evaluated by **Gather evidence** (`POST /api/run/evidence`) against the EOC's work items: `items` filters by `cat` (one or a list), `key_prefix`, `title_contains`; `expect` checks `min_count`, `max_count` (duplicates: one item per household or shelter), `owner_within_min`, `done_within_min` (wall minutes × the run speed, read from the item's `Owner:` / `Status: done` log lines), `status_in`, `decision`, `no_unowned_high`. The check gets `evidence` text and a `suggest` (✓ / ✗); the controller still records the result. Minutes come from the run's **clock segments** (`clock.segments`: wall time, drill minute and speed at every start / pause / stop / speed change / jump; `Runner.drill_minute(wall_ms)`), so they are exact across speed changes and pauses.
- **Evaluation** (section 2.7): `need` on a `work_item` overrides the rule for its need; `need` on a `voice` / `prompt` / `paper` / `note` card registers a need the EOC must meet (`cat`, `prio`, `owner`, `done`, `decision`, `title_contains`, `label`, `role`; `form` for a report the card carries). `after: {need, is, delay}` makes any inject a consequence: `need` is the inject id, with `#<kind>` for a need the engine derived from a report (`life`, `miss`, `hq`, `nbr`, `local`, `shelter`, `bldg`, `approve`, `report`); `is` is `met` or `overdue`; with `each: unit` the item binds to its unit's need. `kind: reply` posts a `church_eoc_reply` to the EOC: `from`, `match` (`cat`, `status`, `title_contains`; the unit when `each: unit`), `status` (default `done`), `decision`, `text`; it fires only where the simulator plays the line above. `needs.defaults` sets the rule per category (`owner`, `done`, `decision`, `done_states`; `report.typed`). `done.checks` are the scoreboard's done-when lines: `sitrep` + `by`, `no_unowned_high`, `pct_min`, `cat_met`, `need_met` (every need of one inject met).
- Supply Order item ids are the Church catalog ids the forms use (`wa01` bottled water, `gs01` blankets, `kb01` cleaning kits, …), so the EOC's Supply Order tab aggregates them.

| **pseudonymized** | last name kept, first name invented (a man's name for every calling only men hold); every full name unique, and none equals a real full name in the pack | invented, one per person, in the `555-0100` to `555-0199` range reserved for fiction (`<area code>-555-01xx`; no state) | `first.last@churchemcomm.sim`, unique | Tabletops, screenshots, shared runs, bug reports, anything that leaves the room. Default. |

Pseudonyms are deterministic: the invented first name, number and email are derived from a hash of the person id and a per-pack salt, so the same person gets the same pseudonym in every run and across the Stake and Area laptops, and a different pack gets different pseudonyms. Organization names, buildings and addresses are not changed in either mode (they are public on the Church's meetinghouse locator), but they still never enter the repository because they come from the pack. The mode is stamped in the pack, in every generated run, in the EOC notes the run posts, and in exported hot-wash text.

## 6. Maps in the EOC Message Center and on the wall (UX design: the user experience)

The geographic dataset gives stake and ward boundaries, meetinghouses and source-map artwork. On the EOC screens a map earns its place only where it answers an operator's question faster than a list does. Three places do:

1. **Message Center → Map tab** ("where are we?"): the stake's wards drawn as outlines, each filled by **roster status** — not reported (grey), reported and fine (green), reported with needs (amber), alert such as missionaries not accounted for or injuries (red), overdue against the expected check-in (amber outline). Meetinghouses as dots, with this EOC, its Satellite EOCs and the parent EOC marked. Reports with a GPS (Global Positioning System) fix plotted as small form icons. Click a ward: its roster row, its reports and an **Open** link. Legend and PACE badge in a corner. At the Area level the same map shows stakes instead of wards. Nothing moves on its own; the operator pans and zooms.
2. **Wall display → map tile** ("what does the room need to see?"): a non-interactive copy of the same status map, auto-fitted to the EOC's units, placed where the roster tile is today when the map data is available (the roster list shifts right). Colours only; no labels smaller than 18 px; a count line under it ("7 of 9 wards reported · 2 with needs").
3. **Simulator** (already built): the full map with overlay artwork, measuring and selection, for planning Satellite EOC sites and seeing scenario severity.

What **not** to do: no map on the phone page (bandwidth, screen, and it would need the dataset on the phone); no source-map artwork on the wall (it is busy and the colours fight the status fill); no map in standalone mode without a server unless the operator points the page at the dataset folder (a later option via the browser's folder picker).

Mechanics, in the same style as the rest of the project:

- The EOC server gets an optional **map data path** (startup argument or `PUT /api/map/config`, like the Drop Folder path) and serves `/map/…` from that folder's `simulator/` subtree only, exactly as the simulator server does. No path configured means no Map tab and no wall tile; everything else is unchanged.
- One **map module** (`templates/_shared/emcomm-map.js`, the canvas renderer from the simulator page cut down to boundaries, points and status fills) is inlined into the Message Center, the wall and the simulator by `installer/sync-app-module.py`'s pattern, so there is one source, as with the app module.
- Status comes from data the pages already hold (roster, messages, incident), so the map is a view, not a new store. Ward names in the roster must match the dataset's unit names; the Setup tab's "units covered" list is filled from the dataset when the map path is set (**From map data**, built 2026-10-31: reads `/map/organization_boundaries.geojson`, picks the stake whose name is in the EOC's name, ticks its wards and branches, or the stakes at a Council / Area EOC; a Satellite EOC starts with nothing ticked), which also fixes the names.
- Versions: the server learns new endpoints, so `FORMS_VERSION`, `APP_VERSION` and `CACHE` move together as usual.
